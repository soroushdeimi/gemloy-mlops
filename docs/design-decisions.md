# Design decisions and evidence

## Model and version

Keep Gemma 4 26B-A4B. The [checkpoint card](https://huggingface.co/cyankiwi/gemma-4-26B-A4B-it-AWQ-4bit) exists; its [configuration](https://huggingface.co/cyankiwi/gemma-4-26B-A4B-it-AWQ-4bit/blob/5c5db8a7aeabb70b27923ef56536aa5343ecbb5b/config.json) identifies packed integer weights and `compressed-tensors`. AWQ in the repository name describes calibration, so the serving flag is `--quantization=compressed-tensors`, not `awq`. Revision `5c5db8a7aeabb70b27923ef56536aa5343ecbb5b` is pinned from the public commit history; no weights were downloaded here.

Pin the serving container to release `v0.25.0`. The [tagged Gemma implementation](https://github.com/vllm-project/vllm/blob/v0.25.0/vllm/model_executor/models/gemma4.py) contains the model and passes quantization configuration into its layers. The [tagged compressed-tensors implementation](https://github.com/vllm-project/vllm/blob/v0.25.0/vllm/model_executor/layers/quantization/compressed_tensors/compressed_tensors.py) and [MoE dispatch](https://github.com/vllm-project/vllm/blob/v0.25.0/vllm/model_executor/layers/quantization/compressed_tensors/compressed_tensors_moe/compressed_tensors_moe.py) support integer weight-only serving. These establish software support, not a measured fit or throughput on this card. Kernel selection and output quality still require the real node. The [tagged container definition](https://github.com/vllm-project/vllm/blob/v0.25.0/docker/Dockerfile) uses CUDA 13.0.2 and the `vllm serve` entrypoint; the chart passes a positional model directory. The proposed driver branch must satisfy that runtime.

## VRAM calculation

The hardware capacity is 24 GiB (24,576 MiB), measured on the current llama.cpp host deployment; source: measurements from the existing single-host llama.cpp deployment (operator notes, not part of this repo). The following is a conservative planning calculation, not a measurement. All parameters must reside in memory even though only a subset is active per token.

| Component | Budget and calculation |
|---|---|
| Checkpoint weight files | 17,191,345,100 / 2^30 = 16.0107 GiB, reported as 16.01 GiB. Includes quantization metadata and unquantized tensors; no extra assumed weight allowance. |
| BF16 KV upper bound for two full contexts | 2 sequences × 2048 tokens × 30 layers × 2 (K,V) × 8 KV heads × 512 maximum head dimension × 2 bytes / 2^30 = 1.875 GiB. Deliberately bounds mixed sliding/global attention without assuming cache sharing. Dimensions come from checkpoint config. |
| Activations, CUDA context, workspaces | Assumed 2.5 GiB starting reserve; eager execution avoids captured CUDA graphs. Must confirm runtime overhead on the node. |
| Planned total for requested contexts | 16.0107 + 1.875 + 2.5 = 20.3857 GiB |
| vLLM allocation ceiling | 24 × 0.90 = 21.6 GiB |
| External headroom | 24 − 21.6 = 2.4 GiB |
| Remaining budget beyond requested contexts | 21.6 − 20.3857 = 1.2143 GiB |

The weight sizes come from the [model metadata API](https://huggingface.co/api/models/cyankiwi/gemma-4-26B-A4B-it-AWQ-4bit?blobs=true), checked at [the pinned revision](https://huggingface.co/api/models/cyankiwi/gemma-4-26B-A4B-it-AWQ-4bit/revision/5c5db8a7aeabb70b27923ef56536aa5343ecbb5b?blobs=true). The four `.safetensors` byte sizes are 5,369,790,400 + 5,370,207,662 + 5,362,493,774 + 1,088,853,264 = 17,191,345,100. Part of these files may be the vision tower that `--language-model-only` skips; charging the full serialized size is a conservative starting estimate, not a measured resident allocation. Loading, repacking and allocator behavior can still change the runtime footprint.

Start with `--gpu-memory-utilization=0.90`, `--max-model-len=2048`, `--max-num-seqs=2`, `--max-num-batched-tokens=512`, `--kv-cache-dtype=auto` with `--dtype=bfloat16` (BF16), and `--enforce-eager`. BF16 follows the checkpoint configuration and avoids the FP16 overflow concern for Gemma; the Ampere RTX 3090 supports BF16. Batch tokens = context / 4 is a deliberate prefill workspace reduction. No FP8 requirement is imposed on the RTX card. `--language-model-only` removes unused visual execution; serving alias is `--served-model-name=gemma4-summary`.

vLLM assigns KV cache the memory remaining after profiling weights and runtime overhead, rather than limiting it to the requested-context row. With the assumptions above, the available KV budget is 21.6 − 16.0107 − 2.5 = 3.0893 GiB. The conservative per-token bound is 30 × 2 × 8 × 512 × 2 = 491,520 bytes, so aggregate KV token capacity is approximately floor(3.0893 × 2^30 / 491,520) = 6,748 tokens before block rounding. Two full requested contexts need 2 × 2048 = 4096 tokens, below this estimate. Mixed attention can reduce actual per-token storage. Confirm the resulting KV token capacity and concurrency estimate from the startup log; do not present this planning bound as measured capacity.

At commissioning, inspect actual loaded weights, non-torch memory and reported KV token capacity before traffic. If initialization fails, reduce max model length by half: 1024 gives a KV upper bound of 0.9375 GiB for two full contexts. If weights alone exceed the budget, a smaller supported checkpoint needs an explicit new budget; do not silently offload or replace this checkpoint. Do not claim this deployment fits until that test passes.

## Resource and policy derivations

Values are proposed operating budgets, not observed performance. App CPU request is one tenth of a core and limit one core; memory request is half its 256 MiB limit. Model host RAM request is half its 16 GiB limit, leaving half the documented 32 GB host RAM for OS, k3s and other services; verify the distinction between GB and GiB on the installed OS. Two requested CPU cores and four limited cores are reservations for a GPU process, not a throughput prediction. Shared memory is 16 / 8 = 2 GiB and counts against pod memory. Cache disk is rounded up from three 16.9 GB reference weight copies: 3 × 16.9 / 1.073741824 = 47.22 GiB, rounded up to a 50 GiB allocation; checkpoint size and free space must be checked. A completion marker is written only after a successful pinned revision download; cache content is reused thereafter. Each revision uses `/cache/models/REVISION` and its own `.complete` marker, so rollback selects the correct retained directory. Remove old revisions only after confirming the serving pod no longer uses them.

On a cache miss, the init container installs pinned `huggingface-hub==0.34.4` into an ephemeral directory to ensure the required legacy `huggingface-cli download` command exists independently of the serving image's tooling. This needs package-index access at deployment. HF token comes from an optional Secret; public files need no token. Private/gated checkpoints require license access and a sealed token. Cache files are not committed.

Startup allowance = 180 failures × 10 seconds = 30 minutes, excluding init download time. Liveness allows 5 × 30 = 150 seconds of failures after startup; readiness checks every 10 seconds. These are proposed recovery budgets, not measured cold-load times. App startup allows 30 × 2 = 60 seconds. App request deadline is 180 seconds; each upstream attempt has a 120-second timeout, connect/pool timeouts are 5 seconds; at most three attempts with 0.25 + 0.5 = 0.75 seconds backoff, bounded by the overall deadline. Only connection failures and server errors retry. Read/write/pool timeouts map to 504; exhausted connect failures and invalid/upstream HTTP responses map to 502, except an upstream 400 mentioning context/token length maps to 422 with "input too long for model context". Other validation also produces 422.

App output cap = context / 4 = 512 tokens; default = cap / 2 = 256; minimum = cap / 32 = 16. Input budget = 2048 context − 512 maximum output − 64 template/system allowance = 1472 tokens. At an assumed 3.5 characters per token, 1472 × 3.5 = 5152 characters, rounded down to a default cap of 5000. `MAX_INPUT_CHARS` (default 5000) and `MODEL_CONTEXT_TOKENS` (default 2048) are environment settings read at process startup. Effective input cap is the smaller of `MAX_INPUT_CHARS` and floor((`MODEL_CONTEXT_TOKENS` − 512 − 64) × 3.5); a nonpositive cap prevents startup. The Helm app values `maxInputChars` and `modelContextTokens` and the plain manifests supply the same defaults. Keep `modelContextTokens` synchronized with the vLLM chart's `model.maxModelLen` when changing context. This character estimate is not a token guarantee: token-heavy inputs can still exceed context, so upstream context-length errors return 422 without retry. Readiness HTTP timeout is three seconds, below its five-second probe timeout; pooled HTTP connections cap at ten with five kept alive (half retained). Histogram buckets are deliberately sparse sample boundaries spanning subsecond through the five-minute upper bucket; they do not represent measured latency.

## Trade-offs

k3s minimizes control-plane administration and includes containerd, local-path and metrics-server. One control plane and local disks do not provide high availability. Native Ubuntu is the target; Windows/WSL is unsuitable as an assumed equivalent GPU Operator environment.

GPU Operator owns discovery, device exposure and telemetry; driver and toolkit stay operator-managed to avoid duplicate installation. Recreate intentionally causes model outage on updates. Local-path avoids network storage dependencies but binds weights to one node; replacing that node requires restoring or downloading the cache.

vLLM provides queue and KV telemetry and continuous batching. Existing llama.cpp build `10850-f114f91f9` with GGUF Q4_K_M and `--parallel 2` is the working alternative, measured on the current llama.cpp host deployment — source: measurements from the existing single-host llama.cpp deployment (operator notes, not part of this repo). Its GGUF file is not the packed checkpoint used here. Migration needs quality and latency comparisons; throughput from that host is not a vLLM forecast.

App Helm and plain delivery are alternatives. Install exactly one with the same service identity. HPA grows app capacity only; it cannot create GPU capacity. See [scaling](scaling.md). Monitoring thresholds are initial policies with calculations in [monitoring](monitoring.md).
